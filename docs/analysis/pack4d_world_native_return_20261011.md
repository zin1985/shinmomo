# マップ0x4Dの実機往復と新しいnative復帰接続

2026-10-11 / zin1985/shinmomo

## 結論

cfg_t04_l006_v2（pack 0x4D）と世界マップ
cfg_t01_l001_v1（pack 0x4C）の往復が成立した。

既存の「世界(52,233) → 0x4D(17,37)」はCC:0AF9の
静的座標候補と実機の一致で確定済み。今回、
**0x4D(17,37) → 世界(52,233)** を新たに実機確認した。
これは既存遷移候補に無かった逆方向なので、
Viewerに1件だけ新しい接続として追加した。

| 観測 | エミュフレーム | WRAM |
| --- | ---: | --- |
| pack0x4Dで南端(17,37)に待機 | 663378 | $0305=0x4D |
| 一歩南の境界外(17,38) | **663382** | まだ0x4D |
| 世界への復帰、座標(52,233) | **663387** | $0305=0x4C |
| 生VM領域 $126E/$12B4 が0x4Cに収束 | **663414** | pack0x4C |
| 無入力120フレーム後 | 663523 | pack0x4C、(52,233)で安定 |

再生は非表示BizHawkの専用ステート
vmtrace_pack4d_south_ready_x17_y37_20261011.Stateを使用。
SNESのDownだけ25フレーム実行し、後続の120フレームは無入力。
最初のロード後は操作受付のため約80フレーム待つ必要があった。
待機が不十分な状況では方向入力をしても座標が動かず、
ただちに「出口が無い」と結論できない。

## ROMと実機の照合

data/maps/transitions/map_native_bounds_catalog.csvで確認した
pack0x4Dの静的native境界：
- マップ構成 cfg_t04_l006_v2、タイルセット4、レイアウト6
- 原典境界命令 CC:18AB
- X=1..46、Y=1..37

実機でY=38への境界越えを確認したため、静的範囲と一致。
独立した世界→0x4D実機証拠
world_52_233_entry_verified_20261011.json が
pack0x4D到着(17,37)を担保する。

検証スクリプト
tools/python/verify_native_pack4d_world_return.py は
正確な境界越え、pack切替、座標、VM領域収束、
無入力安定120フレーム、源マップの独立証拠を必須とする。
派生メタデータ：
data/maps/transitions/pack4d_south_native_return_20261011.json。

tools/python/add_runtime_native_return_edge.py は
実機・ROM照合が成功したときのみ
runtime_native_pack4d_south_return_20261011 を挿入する。
既存に同じ向きの接続があれば必ず拒否する。
CPU実行フック由来の命令PCは**未確認**。
native境界復帰をVM0x56発火と誤認しない。
「現在のストーリー状態で通行可能」は**unknown**であり、
Viewerは実行シミュレーションではなく研究用の閲覧機能。

注意：この経路では生$0306が120フレーム後も0x4Dで、
$126E/$12B4の0x4C収束とは一致しない。
あらゆる生WRAM項目が同時に目的packへ変わるとは仮定しない。
